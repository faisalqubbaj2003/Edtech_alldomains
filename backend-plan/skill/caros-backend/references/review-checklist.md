# Reviewing a diff as the second model

The build rule is that the model which reviews a change is not the model which wrote it: Opus 5.5 writes, Fable 5.1 reviews the tasks marked `F`, and where the B0 bake-off moved a category back to Fable, Opus reviews Fable. A model reviewing its own reasoning tends to agree with it. Your value here is that you did not write this, so read it as someone who expects to find the mistake.

## What you may see

You review **the diff, the brief, the acceptance list and synthetic test data only**. Fable 5.1 is an Anthropic Covered Model: its prompts are retained for at least 30 days, which is why it never sees tenant data. If the diff, a fixture, a log excerpt or a screenshot contains anything that looks like a real student, parent or staff member (a name not on the synthetic rosters, a real email domain, a real student number), stop, do not quote it, and write a "request changes" verdict whose only finding is where you saw it.

## Read in this order

1. The brief in `docs/PLAN.md`: what "done when" promised, and what was out of scope.
2. The spec sections the brief names under `docs/spec/`.
3. The tests in the diff, before the code. Ask whether each "done when" line has a test that would fail if the code were wrong, including a **negative** case. A permission test that only checks the allowed path proves nothing about the forbidden one.
4. The code.

## Where to look hardest

These are the places where a mistake is silent: the tests pass, the demo works, and the flaw only shows as a leak or a wrong decision months later. Each item names a trap the planning review already found once, so you know what it looks like.

**Authorization and row-level security**
- Every tenant table: `school_id` first, RLS enabled **and** `FORCE`d, the tenant policy `RESTRICTIVE`, and a query with no tenant context sees nothing (test it).
- `SECURITY DEFINER` functions: inside one, `current_user` is the function's **owner**, not the caller. A check like `current_user = 'caros_t_system'` inside a definer function is always false or always true. The tier must be evaluated in the policy expression (which runs as the caller) and passed in as an argument. (Pass 7 finding F01.)
- Login roles are per deployable (web, worker, migrator, support console), `NOINHERIT`, and the web identity cannot `SET ROLE` to system or support. Look for a test proving it.
- A verb other than plain write (`escalate`, `approve`, `configure`) must work through RLS, not only in the domain layer; otherwise the first real escalation is refused, and the tempting quick fix is a broad `write` grant that widens access everywhere. (F02.)
- A new permission row with a qualifier ("own only", "aggregates only", "existence and status only") needs the mechanism that enforces the qualifier **and** a negative test. A qualifier with no mechanism is just a comment.

**Transactions and audit**
- The change, its `audit.record()` and its `events.emit()` commit in one transaction. An audit write after the commit, or in a separate connection, can be lost.
- Audit entries and emails carry identifiers and roles only. No student name, no welfare detail, in either.
- Reads of sensitive classes write an access entry at the granularity the class requires.

**Safeguarding**
- One open escalation per case, a repeated idempotency key is a no-op, and the engine cannot lower or close a case a person has escalated.
- The student-disclosure screen in v1 is a lexicon, and nothing a model returns may clear, close or lower a hit. Every hit reaches a person. (F03, decision C1.)
- The safeguarding title, the regulator and any clause number come from the tenant and its regulator profile, never a literal.

**The signal engine**
- Purity: no I/O, database, clock or randomness in `packages/engine`. Same input, same output.
- Check the statistics against the spec's formulas, not against intuition. The review found that per-lesson attendance turned one sick day into a strong signal, and that an uncapped CUSUM kept a single outlier alive for about twelve weeks, so the positive tier almost never fired. (F05.) Ask for each detector: what does one ordinary bad week do, and how long until it clears?
- Expected results in tests must be generated by running the rules, not written by hand, and an acceptance test must be passable with the history the fixture actually carries. (F06.)
- No comparison between students anywhere: no ranking, no percentile, no cohort mean feeding a student's level (except the documented common-cause guard).

**Migrations**
- A migration already on `main` is never edited; a correction is a new migration.
- Drizzle's migrator runs all pending migrations in one transaction, which breaks `CREATE INDEX CONCURRENTLY`. Look for how the diff handles it.
- Expand and contract: a column or table is dropped two releases after nothing reads it, not in the same change.
- Anything touching `auth.*` or `audit.*` gets your review regardless of the task line.

**The AI gateway**
- Only models on the registry with `covered_model = false` and `zdr_eligible = true`, with `inference_geo` pinned. No Batch API, Files API or other ZDR-ineligible endpoint for anything student-derived.
- Pseudonymisation happens before the request leaves, and the excluded classes (safeguarding, health, nationality, fairness labels, the counselor log) never enter a prompt at all.
- No tenant-specific string inside a structured-output schema (schemas are cached).
- Model output is a labelled draft. It never gates, ranks, or decides.

**Portability**
- Nothing ACS-shaped as a literal: "Grade", a year number, "Child Protection Officer", "ADEK", an ACS person's name, a fixed school week. The Wellesmere tenant (British, Years 10 to 13, DSL, no IB) should pass the same tests.

**Process**
- `docs/PLAN.md` is updated in the same PR (task line, attempts, session note).
- No file was replaced wholesale. If a large file's diff is mostly delete-and-re-add, ask why.
- Nothing outside the brief's scope slipped in.

## The verdict

Post it on the PR in this shape, and keep it to what you would stand behind:

```
Verdict: approve | request changes
Checked against: <brief id>, <spec sections>
Findings (most severe first):
- [blocking|serious|minor] <file:line> What is wrong. Why it matters here. The fix.
Tests: <which "done when" lines have a real test, which do not>
Not reviewed: <anything you could not assess, and why>
```

"Request changes" blocks the merge until the finding is fixed or Davide overrules it in writing on the PR. Use it for anything that is wrong, not for taste. If you found nothing, say what you checked, so an approval means something.
